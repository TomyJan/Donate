# 后续开发方向

以下为代码与文档梳理后的建议，尚未排期或实现。核心捐赠、自动 / 手动补单、持久队列管理、身份绑定、会话续期、属地更新和备份恢复已具备，不宜再搭一套重复能力。

## 优先：运行可靠性

1. **故障主动通知。** 现有健康端点检查数据库与日志状态，任务页可查看失败，但没有通知渠道。先复用外部监测与 JSONL，观察持续网关错误、已到期任务积压、备份过旧和磁盘空间；再按需要增加轻量只读运行摘要。通知设置持续阈值、合并和恢复消息，勿把未来计划任务当作积压。
2. **恢复演练与核对报告。** 现有一致性备份和离线恢复可继续使用；补一次异机副本的隔离恢复演练。若需要开发工具，优先只读报告：恢复点、金额 / 条数、未完成任务及恢复后需核对的操作，不自动重建已删订单或强制入账。
3. **真实渠道验收留档。** 按[支付清单](payment-integration.md#上线核对)记录实际网关、两种渠道、漏通知和关单结果；登录也记录 QQ / OIDC 的 claims 与头像样本。先确认已有生产验收证据，缺哪项补哪项，不用 CI 通过代替外部能力验证。

## 有实际需求再做

| 方向 | 触发条件与边界 |
| --- | --- |
| 支付凭据版本化 | 需不中断轮换商户 / 密钥时，按订单配置版本选择凭据并定义过渡期；当前仅一组配置，先遵守切换限制 |
| 更严格的网关响应解析 | 对重复 JSON 键、扩展字段和签名歧义建立明确拒绝规则及兼容测试，再改解析器；不把通知表单校验误认为响应 JSON 已有同样保证 |
| 服务端条款确认记录 | 若需要证明用户同意具体条款版本，再统一站内弹窗和外部 IdP 入口；当前仅本机确认，不是服务端签署记录 |
| 后台组件拆分 | 新增后台功能时将概览等独立 feature 提取，保留请求 scope 与共享详情；避免仅为目录整齐重写状态管理 |

暂不引入 Redis、微服务或通用配置中心。退款、账号合并、用户自助解绑和批量强制补单会改变现有产品 / 安全边界，应另行确认需求。
