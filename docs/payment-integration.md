# 彩虹易支付接入方案

新版采用彩虹易支付 **V2 优先、V1 显式兼容**，共用订单、通知校验和补单状态机。协议由部署配置选择，写入每笔订单；不因超时、验签失败或返回错误自动换协议重下单。本文是后端设计的一部分，尚未进行商户联调或真实交易。

## 协议范围与证据

公开资料里的“易支付版本”需要区分软件版本、SDK 版本和商户 API 协议。SDK V1.3 / V2.0 不代表存在第三套订单 API；兼容程序也可能更改状态值和响应结构，不能仅凭名称混用。

本次核对了部署站的 [V1 文档](https://pay.v8jisu.cn/doc/v1_legacy_api.html)、[V2 协议说明](https://pay.v8jisu.cn/doc/index.html)和[签名规则](https://pay.v8jisu.cn/doc/sign_note.html)，以及公开源码镜像内附的接口文档、PHP SDK 与处理器。镜像固定为 [`maajiko/Epay@a4d0f04`](https://github.com/maajiko/Epay/tree/a4d0f0421cfcbc573913c8007bde3d0c04a5713a)，它不是本项目当前商户部署版本的证明，也不作为官方最新版本声明。部分在线文档当前返回错误页，因此关键结论同时给出可定位的源码证据；不把搜索快照当作生产接口已验证。

| 项目 | V1 传统协议 | V2 RSA 协议 |
| --- | --- | --- |
| 编码 | UTF-8，表单编码 | UTF-8，表单编码；不是 JSON 请求 |
| 页面跳转下单 | `submit.php`，GET / POST | `api/pay/submit`，GET / POST |
| 服务端下单 | `mapi.php`，POST | `api/pay/create`，POST |
| 单笔查单 | `api.php?act=order`，传统实现读取 GET 参数 | `api/pay/query`，POST |
| 下单 / 查单成功码 | `code=1` | `code=0` |
| 凭据与签名 | pid + 商户 key；支付参数采用 MD5，旧查单直接提交 key | pid + 商户私钥 + 平台公钥；RSA-SHA256，`sign_type=RSA` |
| 时间戳 | 传统协议没有统一时间戳约束 | 请求、成功响应及通知带 Unix 秒级 timestamp；所查 SDK 验证正负 300 秒窗口 |
| 通知 | GET，MD5 验签，`TRADE_SUCCESS`；提交成功后回应 `success` | GET，平台公钥验签，`TRADE_SUCCESS`；提交成功后回应 `success` |
| 关单 | 所查传统 V1 公共文档没有标准关单入口 | `api/pay/close`，POST；只有部分支付插件支持 |

V2 的[下单文档](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/template/default/doc/pay_create.php)中，`method=jump` 表示只返回跳转 URL，支付渠道仍放 `type=alipay` 或 `type=wxpay`；不能与其他兼容平台把 method / type 调换的文档混用。金额在网关协议中为**元的十进制字符串**，本站内部与 API 仍为整数分。

## 本项目的接入选择

V2 请求实际使用 PHP 原生入口：POST `api.php?s=pay/create`、`api.php?s=pay/query`、`api.php?s=pay/close`，分别对应文档的 `/api/pay/*`，由同一个处理器执行。这样无需网关安装 URL 重写规则；支付参数仍在 POST 表单中，RSA 签名和验签不变。

1. 默认 `EPAY_PROTOCOL=v2`，配置网关基址、pid、商户私钥、平台公钥。私钥从部署文件或环境变量读取，不放前端、源码或日志。优先采用服务端 `api/pay/create`、`method=jump`，验签成功后保存平台流水和跳转结果，再让浏览器跳往平台支付页；不增加本站扫码页 / JSAPI 流程。
2. V1 由管理员部署时明确选择 `EPAY_PROTOCOL=v1`，使用 pid + key。以服务端构造的受控表单 POST 到 `submit.php` 跳转支付，查询调用传统 `api.php?act=order`。不假设它支持 POST 查单、请求头传 key 或某个二开新增接口。只有实际部署协议证实后才增加适配。
3. 订单保存协议、商户配置标识、平台流水 `trade_no`，以及有实际返回时的支付渠道流水 `api_trade_no`；两种流水不混同。商户单号使用站内 ID 去横杠的 32 位十六进制编码，须通过实际部署的字符 / 长度约束测试。
4. V2 创建过程使用订单级并发协调，同一订单只允许一个创建调用在途；成功结果复用。超时先查原商户单号，保留“提交结果未知”，不得换单号、换协议或换商户重发。确需重试时仍使用原单号与相同业务参数，并核实网关的重复单处理。
5. 回调按订单中已固定的协议和商户配置选择验签器；`sign_type` 不得由来访参数任意切换。切换默认协议只影响新订单，旧订单仍按原协议处理，旧凭据的保留 / 轮换须覆盖未结束订单。
6. 下单商品名称固定为“捐赠 TomyJan”，不把用户留言或身份资料发送为商品名称 / param。跳转地址和签名字段不进分析日志，不执行上游返回的任意 HTML；V2 只接受已声明的 jump 结果并验证 URL 协议及允许目标。

网关可能返回外部通道的跳转域名，因此跳转目标使用部署侧明确的 HTTPS 域名允许列表；默认允许本网关。新增通道域名需核对提供方文档 / 联调结果，不能为了兼容而接受任意 URL 或开放重定向。对仅有扫码、JSAPI 或其他结果的异常配置明确报不支持，不在已有设计中偷偷增加支付方式。

## 签名、响应与日志

签名参数按名称 ASCII 排序，排除 `sign`、`sign_type` 及协议定义的空值；构造签名串时使用原始标量值，不做 URL 编码，之后才进行传输编码。值 `0` 必须保留，不能照搬 PHP `array_filter` 把它当空值去掉。V1 在字符串后追加 key 计算小写 MD5；V2 使用 RSA PKCS#1 v1.5 + SHA-256，签名做 Base64，Go 使用标准密码库。

V2 成功响应、查询结果和通知必须验证平台签名与时间戳；签名计算纳入符合协议的新增标量字段，业务 DTO 只读取白名单字段。拒绝重复参数、数组 / 嵌套类型、畸形数字、错误签名类型和无签名的“成功”。未签名的错误响应最多作为调用失败，不能证明未付款或关单成功。时间过期且签名有效的通知不直接入账，可提前既有查单任务取得新鲜结果；不能靠延长时间窗口代替补单。通知重试次数和每次是否刷新 timestamp 仍需实际版本联调。

V1 查单的 key 在 URL 中，必须只由服务端经 HTTPS 调用；出站日志 / tracing / HTTP 错误包装统一删除 query，不让网络错误中的完整 URL 带出 key。不调用不必要的商户信息接口，避免其返回 key 等敏感字段。V1 查询不具备 V2 的响应签名能力，信任边界是配置中的 HTTPS 网关，严格核对商户、订单、金额、流水和渠道后才能应用。

SDK 只用于核对协议，不直接移植其关闭 TLS 校验等示例行为。本站始终验证 TLS；不使用 SDK 附带的示例密钥。

## 查询能补什么、不能补什么

所查 [V2 查询处理器](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/includes/lib/api/Pay.php)的 `query()` 直接读取平台订单表，V1 的 [order 处理器](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/api.php)同样如此，并未在这个接口里实时调用支付宝 / 微信。

因此，本站自动 / 手动补单核对的是**易支付已记录的支付结果**，可以修复易支付已到账但本站漏通知的情况；若易支付自己仍漏记，需要它的后台任务 / 通道能力先核实，本站不能伪称已经直查支付宝 / 微信。平台持续返回未付时保留核验记录，不由管理员强制改 paid。

所查 [V2 查询文档](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/template/default/doc/pay_query.php)定义 `status=0` 未付、`1` 已付、`2` 退款、`3` 冻结、`4` 预授权。仅 `1` 映射本站 paid；其他非零值不能当作成功。退款 / 冻结 / 预授权属于异常观察，保留网关原状态并告警，不开放本站退款功能，不将本站既有 paid 降级，也不擅自把尚未到账的订单记为捐赠成功。未知状态同样拒绝猜测。

补单调度、24 小时自动窗口、并发去重和人工唤醒沿用[后端设计](backend-design.md)；查询不存在、业务失败、超时都不能当作最终未支付证明。查询结果的金额 `money` 与原订单比较，不用扣费后净额或其他通道的调整金额替代。

## 关单必须区别对待

[关单文档](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/template/default/doc/pay_close.php)明确由部分支付插件提供；[Order::close](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/includes/lib/Order.php)调用[插件 close](https://github.com/maajiko/Epay/blob/a4d0f0421cfcbc573913c8007bde3d0c04a5713a/includes/lib/Plugin.php)，不能仅凭 V2 接口存在就认定所选支付宝 / 微信通道可关闭。

更重要的是，这份查询状态列表**没有独立的“已关闭”值**，所查公共 close 包装也没有统一把平台订单状态改成 closed。实现必须另存经过验签的关单操作结果及时间：

- 查询仍为 `0` 只说明平台记录未付，不能据此显示远端关单成功。
- 对接通道经验证支持关单且返回有效签名成功，才能记录“远端已确认关单”；再查一次用于发现并发到账，不要求查询凭空返回 closed。
- 未支持、超时或未知错误，保留“本站已关闭 / 远端未确认”，按既定计划继续兜底。成功关单后的最终核验若失败，也暂不取消兜底；若明确证明远端已终止且未到账，可结束普通轮询。
- 本地关闭 / 到期不会凭空作废用户已经打开的远端页面；后续有效到账仍按真实结果入账。删除仍是真删除，不重建订单。

## 联调验收

普通 CI 使用按上述协议制作的测试网关，不依赖真实商户；上线前用实际部署验证两种渠道的创建、回跳、通知、查询、重复单和关单能力。V2 验证 code=0、签名 / timestamp 和 `method=jump`；V1 验证 code=1、GET 查单及字段格式。分别模拟漏本站通知、查单超时、到期后到账、关单不支持、签名响应被篡改、重复参数与状态 2 / 3 / 4。

协议资料已足够推进开发，不需要用户再寻找通用文档。尚不能从公开资料证明的是**当前商户部署支持哪套协议、开放哪些通道和额度，以及具体关单能力**；这些在配置实际网关与测试凭据时核验，不提前声称已通过。
